# データベース設計書

このドキュメントは、ShifPita MVPのデータベース設計に関する全体方針と構造を定義します。
個々のテーブルの物理的な定義は `tables.md` を、エンティティ間の関連は `relationships.md` を参照してください。

---

## 1. 設計思想・方針

本アプリケーションのデータベースは、以下の思想に基づいて設計されています。

- **ユーザー中心設計:**
  従来の従業員リストという考え方から、システムにログインする「ユーザー(`User`)」をデータモデルの中心に据えました。これにより、認証情報（パスワード等）と個人情報、役割(`Role`)、そしてそのユーザーに紐づく全ての活動（希望休申請、シフト割り当て）を一元的に管理できます。

- **履歴の保持:**
  いつ、誰が、どのシフトを生成したかを記録するため、「シフト生成履歴(`Transaction`)」テーブルを導入しました。これにより、過去に生成されたシフトをバージョンとして管理し、将来的な監査や再確認に対応できる拡張性を持たせています。個々のシフト(`Shift`)は、この`Transaction`に紐付きます。

- **正規化:**
  繰り返し発生するデータ（役割名、シフトのパターン名など）は、それぞれ`roles`、`shift_types`としてマスタテーブルに分離し、各テーブルからは外部キーで参照します。これにより、データの一貫性を保ち、変更を容易にしています。

- **柔軟性の確保:**
  シフト生成のルールなど、将来的に変更される可能性が高い固定値は `master` テーブルでキー・バリュー形式で管理し、コードの変更なしに設定を更新できる仕組みを目指します。

---

## 2. 主要テーブルの役割

- **`users`, `roles`:**
  認証と認可の基盤です。`users`テーブルがログインユーザー情報を保持し、`roles`テーブルへの外部キーを通じてそのユーザーが「管理者」なのか「一般従業員」なのかを判断します。

- **`shift_types`, `master`:**
  シフトパターンの定義やアプリケーション全体の設定を管理するマスタデータです。これらのデータをユーザーが（将来的にはUIから）編集可能にすることで、アプリケーションの柔軟性を高めます。

- **`day_off_requests`:**
  ユーザーからの希望休申請を記録するトランザクションデータです。シフト生成ロジックは、このテーブルを参照して制約条件とします。

- **`transactions`, `shifts`:**
  シフト生成の結果を保存するトランザクションデータです。`transactions`が「2026年10月分のシフト」といった生成単位を、`shifts`が「Aさんが10月1日に早番」といった個々の割り当てを示します。

---

## 3. インデックス戦略

パフォーマンスを確保するため、以下のカラムにはインデックスを設定します。

- **主キー (`id`):** 全てのテーブルの主キーには自動的にインデックスが作成されます。
- **外部キー:** 全ての外部キー（例: `users.role_id`, `shifts.user_id`）にインデックスを設定し、テーブル結合（JOIN）のパフォーマンスを向上させます。
- **ユニークキー:** `users.username` や `roles.name` など、一意性が求められるカラムにはUNIQUEインデックスを設定し、データ整合性と検索速度を両立させます。
- **複合キー:** 複数のカラムを組み合わせて検索することが多い場合（例: 特定のユーザーの特定の日付のシフト）、複合インデックスを設定します。
